# テストのアーキテクチャ

[作業規約](../../../AGENTS.md)のテスト方針に沿って、自動テストと手動確認の役割、各層で確かめること、手動確認の手順を定める。

## 設計方針

1. テストは、古典派の方針で書く。
    - 1つの振る舞いを単位とする。部品は本物を組み合わせる。
    - 出力と、操作の後の状態を確かめる。内部の関数の呼び出しは確かめない。
    - 互いに独立させるのは、テスト同士とする。テストごとに別の一時ディレクトリを使う。
2. テストダブルに置き換えるのは、テストで制御する必要がある境界だけとする。mockで呼び出しを確かめるのも、この境界に対してだけとする。
    - 古典派では、プロセスの外の依存を、managed dependency（このアプリだけが使うもの）とunmanaged dependency（ほかからも見えるもの）に分ける。managed dependencyは結合テストで本物を使い、テストダブルに置き換えるのはunmanaged dependencyだけとする。
    - データディレクトリは、managed dependencyなので、本物（一時ディレクトリ）を使う。
    - 乱数は、AIの選択に使う。結果を決めるために、テストダブルに置き換える。
    - 次の2つは、managed dependencyだが、テストダブルに置き換える。古典派の原則から外れる箇所である。
        - KataGo：結果が毎回変わり、重い。CIで本物を動かすと、テストが遅く、不安定になる。
        - サーバー（フロントエンドのテストから見たもの）：本物を動かすには、GoのサーバーとKataGoが要る。
    - この2つを置き換えたことで確かめられない、本物を組み合わせた動作は、層5の手動の確認で補う。
3. コードを、Khorikovの4象限（Vladimir Khorikov『Unit Testing Principles, Practices, and Patterns』第7章）に沿って、ドメインモデル・アルゴリズムとコントローラーに分ける。
    - ドメインモデルとアルゴリズムは、外部への依存を持たない形にする。ここに単体テストを厚く置く。
    - HTTPとMCPのハンドラーはコントローラーとし、ReactのコンポーネントはHumble Objectとする。どちらもドメインロジックを持たない形にする。ここには結合テストを薄く置く。
    - コントローラーやコンポーネントにドメインロジックが残ってテストしにくい（overcomplicated code）ときは、ドメインロジックをドメインモデルへ移し、単体テストで検証できる形にする。
4. 同じことを、複数の層で確かめない。下の層で確かめた場合分けを、上の層で繰り返さない。

## テスト層

### 層1：Goの単体テスト

1. 目的：ドメインモデルとアルゴリズム（規則と変換）を、場合ごとに確かめる。テストはこの層に最も多く置く。テスト数は検証する振る舞いを単位とし、サブテストも1つずつ数える。
2. 対象：
    - 盤の規則（取り、コウ、自殺手）、地の数え方、ownershipからの死石の判定
    - 置石の上限、コミの値域、入力と保存の上限
    - 棋譜ツリーの操作（待った、変化を主分岐にする、局面以降の削除）と、結果を受け付ける条件
    - AIの候補の条件と重み
    - SGFとJSONの読み込みと書き出し
3. 方法：
    - KataGoの解析結果は、決まった値として与える。乱数は種を固定する。
    - 上限は、上限ちょうどと上限を1つ超えた値の両方を確かめる。
    - 設計上調整できる値（上限、制限時間、呼び出し回数、AIの選び方に使う数値など）は、実装が採用した値で確かめる。テストの目的は、その値や式自体を固定することではなく、適用される境界や規則を確かめることにある。
    - 読み込みと書き出しの往復と、書き出しの安定は、fuzzでも確かめる。
    - 読み込みの拒否は、理由ごとに確かめる。理由は、ドメインモデルが返すエラーの種類で見分け、エラーメッセージの文言では見分けない。

### 層2：Goの結合テスト

1. 目的：コントローラーを通した結果を、入口から確かめる。場合分けは層1に任せ、代表的な場合と、層1では届かない場合に絞る。
2. 構成：HTTPとMCPのサーバーを、一時ディレクトリの保存先で動かす。KataGoだけをテストダブルに置き換える。
3. 対象：
    - 入口ごとの受け付けと拒否、HTTPステータスコード
    - 同じ操作が、画面の使うHTTP APIとMCPで同じ結果になること
    - MCPの呼び出し回数の制限
    - AI agentの操作の競合の拒否
    - 保存と、次の起動での復元。読めないファイルの扱い
    - 並行処理（`go test -race`で実行する）
    - 失敗したときの戻し

### 層3：フロントエンドの単体テスト

1. 目的：画面の状態を決めるドメインロジックを確かめる。
2. 対象：Reactの外に置いた関数（コミの入力の解釈、結果の表示文、localStorageから読んだ値の検証、操作できる状態の判定など）

### 層4：フロントエンドの結合テスト

1. 目的：Humble Objectにしたコンポーネントに残る、コントローラーとしての振る舞いを確かめる。
2. 構成：サーバーをテストダブルに置き換え、DOMの上で画面を動かす。要素は、役割（role）とラベルで探す。
3. 対象：
    - AI agentの変更との同期
    - 最も新しい状態を表示すること
    - 競合のときに、編集中の内容を保つこと
    - 操作できない状態での無効化
    - モードごとの盤のクリックとパスの扱い、AIの手を始めることと中止すること
    - localStorageの読み書きの失敗の扱い
    - キー操作
4. 確かめるもの：画面の状態と、サーバーへ送った要求。

### 層5：手動の確認

1. 目的：自動テストの対象にしないものを、受け入れのときに確かめる。
2. 対象：
    - 変更対象の画面の見た目と画面遷移
    - 実際のKataGoと組み合わせた動作

## 自動テストの対象外

1. 見た目と配置、CSS：層5で確かめる。
2. 文言の一字一句：通知やエラーメッセージは、拒否されたかどうかとHTTPステータスコードを確かめる。文言の一部を照合することも、文言を確かめることに当たるので行わない。
3. KataGoとライブラリ自体の振る舞い：KataGoの解析の質、goban・Mantine・dnd-kitの描画は確かめない。
4. 文書の内容：READMEとAGENTS.mdは、レビューで確かめる。

## 実行時期

1. 層1〜4は、CIで毎回実行する。
2. 層5は、配布前や、変更が実環境での動作や画面表示に影響するときに行う。

自動テストの実行方法は[テストと静的検査の実行](../how-to/validate-changes.md)を参照する。

## 手動確認の手順

### 見た目と画面遷移

1. [開発環境での対局作成](../tutorials/first-local-game.md)または[配布版の起動](../../user/how-to/start-app.md)に沿ってアプリを起動する。変更前後を比較するときは、ブラウザの表示領域と対局条件を揃える。
2. 次のうち変更が影響する状態を作り、画面の見た目と操作後の遷移を確かめる。変更前後を比較するときは、同じ操作で状態を再現し、画面を撮って比べる。
    - 対局のない状態、対局の作成の画面
    - 対局中（人の手番、AIの思考中、AIの思考の中止の後）
    - 終局（二連続パスで死石があるとき、投了、持碁）
    - 検討（変化の追加、変化を主分岐にする、局面以降の削除の確認）
    - 解析の表示（候補手、ownership、評価のグラフ）
    - 保存した対局の一覧（検索、名前の変更、削除の確認、並べ替え）
    - 読み込みと書き出し、エラー
3. 変更前後に差がある場合は、意図した変更の範囲かを確認する。

### 実際のKataGoとの通し確認

1. KataGoを設定してアプリを起動し、5路盤で対局を作る。着手して、KataGoの応手が盤面に反映されることを確かめる。
2. 二連続パスまで打ち、死石の表示と結果が正しいことを確かめる。
3. AIの手を中止して待ったをし、最も新しい人の着手が取り消されることを確かめる。
4. MCPでAI agentから "表示中の局面" を取得し、解析と変化の追加ができることを確かめる。
